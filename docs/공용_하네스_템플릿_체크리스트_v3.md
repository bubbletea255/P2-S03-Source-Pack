# 공용 하네스 템플릿 체크리스트 v3

이 문서는 반복 가능한 지식 작업을 Claude Code와 Codex 양쪽에서 실행할 수 있는 하네스로 설계하기 위한 공용 템플릿이다.

v1은 `harness/` 공통 원장과 플랫폼별 adapter 분리를 정리했다.
v2는 최소 형식 충족이 아니라 고품질 산출물까지 강제하는 품질 계약을 추가했다.
v3는 여기에 **실제 파일 생성 템플릿, 산출물 깊이별 schema, 표기 규칙, 복수 하네스/meta-orchestrator 구조**를 더한다.

이 문서는 특정 분야 전용이 아니다.
다만 가치투자처럼 여러 전문 하네스를 장기적으로 축적하고, 최종 판단은 사람이 승인해야 하는 고위험 분석 업무를 염두에 두고 설계한다.

---

# Part 0. 빠른 시작

## 0.1 이 문서의 목적

이 문서는 LLM에게 "하네스를 알아서 잘 만들어줘"라고 던질 때 사용할 공용 설계 매뉴얼이다.

목표는 세 가지다.

1. 같은 업무를 Claude Code와 Codex 양쪽에서 최대한 같은 구조로 실행한다.
2. 중간 산출물, 최종 산출물, 비교 리포트, 개선 기록을 파일로 남긴다.
3. 모델의 자율성에 맡기지 않고, 좋은 결과의 구조를 contract/procedure/schema/rubric에 명시한다.

## 0.2 읽는 방법

| 읽는 사람 또는 목적 | 먼저 볼 곳 |
|---|---|
| 전체 원칙을 이해하려는 사람 | Part 1 |
| 실제 하네스 파일을 만들 LLM | Part 2 |
| 실행 후 비교와 개선을 할 LLM | Part 3 |
| 새 하네스를 요청하려는 사용자 | Part 4 |
| 복수 하네스/meta-orchestrator를 설계하려는 경우 | 1.7, 2.7, 4.1 |

## 0.3 LLM 행동 규칙

LLM은 이 문서를 읽고 특정 예시를 그대로 복사하지 않는다.
먼저 사용자의 업무 목표, 최종 산출물, 산출물 깊이, 단일/복수 하네스 여부를 확인한 뒤 그 업무에 맞는 Phase 구조를 제안한다.

특히 가치투자 21단계처럼 여러 전문 하네스를 만들 계획이 있는 경우, 21개 하네스를 하나의 거대한 Phase 목록으로 합치지 않는다.
각 전문 하네스는 독립적인 contract/procedure/schema/rubric/artifacts를 가진다.
상위 meta-orchestrator는 각 하네스의 세부 작업을 직접 수행하지 않고, 각 하네스의 최종 산출물과 요약을 읽어 전체 흐름을 조율한다.

## 0.4 핵심 원칙 3줄 요약

- 업무 의미는 `harness/`에 두고, Claude/Codex adapter는 얇게 둔다.
- 최종 산출물은 최소 형식만 만족해서는 완료로 보지 않고, 실제 판단·실행·승인에 쓸 수 있어야 한다.
- 단일 하네스로 무리하게 키우지 말고, 전문 영역이 분리되면 복수 하네스 + meta-orchestrator 구조를 고려한다.

# Part 1. 설계 원칙

## 1.1 이 구조가 해결하는 문제

나쁜 구조는 같은 업무 규칙을 여러 곳에 복사한다.

```text
agents/researcher.md
.claude/agents/researcher.md
.agents/skills/researcher/SKILL.md
```

이렇게 되면 시간이 지나면서 규칙이 조금씩 달라진다.

- Claude와 Codex 결과가 다른 이유가 모델 차이인지 지침 차이인지 알기 어렵다.
- 같은 규칙을 여러 파일에서 고쳐야 한다.
- 한쪽만 최신화되어 drift가 생긴다.
- 교차검증과 A/B 테스트가 흐려진다.

그래서 이 템플릿은 공통 원장과 플랫폼 adapter를 분리한다.

```text
harness/               # 공통 업무 원장
.claude/agents/        # Claude Code 실행 adapter
.agents/skills/        # Codex 실행 adapter
```

## 1.2 핵심 원칙

> 업무 의미는 `harness/`에 두고, 플랫폼별 실행 방식은 얇은 adapter로 둔다.

> 최종 산출물은 사용자가 실제로 판단하거나 실행할 수 있을 만큼 충분해야 한다.

> 좋은 결과의 구조를 contract, procedure, schema, rubric에 명시한다.

## 1.3 산출물 깊이 단계

하네스는 산출물 깊이를 명시해야 한다.
명시하지 않으면 기본값은 `표준 리포트`로 둔다.
가치투자, 리스크 분석, 재무 판단, 전략 의사결정은 기본값을 `의사결정급 산출물`로 둔다.

| 단계 | 사용 상황 | 요구 수준 |
|---|---|---|
| 빠른 요약 | 빠른 방향 확인, 초안, 브레인스토밍 | 핵심 결론, 주요 근거, 다음 질문 |
| 표준 리포트 | 일반 업무 산출물, 실행 계획, 비교 검토 | 요약, 상세 근거, 항목별 내역, 대안, 체크리스트 |
| 의사결정급 산출물 | 투자, 재무, 전략, 고위험 판단 | 근거 추적성, 계산표, 가정, 민감도, 반대 근거, 리스크, 사람 승인 지점 |

## 1.4 산출물 깊이에 따른 실행 행동

산출물 깊이는 선언으로 끝나면 안 된다.
Orchestrator와 각 Phase는 깊이에 따라 조사, 분석, 검증 강도를 다르게 적용한다.

| 깊이 | 조사 | 분석 | 검증 | 최종 산출물 |
|---|---|---|---|---|
| 빠른 요약 | 핵심 자료 중심 | 주요 판단만 | 필수 오류 점검 | 3-4개 핵심 섹션 |
| 표준 리포트 | 복수 자료 확인 | 항목별 근거와 대안 | 누락·모순 점검 | 5-7개 섹션 |
| 의사결정급 | 원자료 우선, 출처 품질 평가 | 가정, 시나리오, 반대 관점 포함 | 계산·논리·출처·리스크 검증 | 8개 이상 섹션, 사람 승인 지점 |

## 1.5 산출물 품질 계약

각 최종 산출물은 최소 형식만 만족해서는 완료로 보지 않는다.
사용자가 실제 의사결정, 실행, 검토, 승인에 사용할 수 있어야 한다.

최종 산출물 schema에는 업무 성격과 산출물 깊이에 맞게 아래 요소를 포함한다.

| 요소 | 의미 | 산출물에 드러나는 형태 |
|---|---|---|
| 핵심 요약 | 가장 중요한 결론과 판단 | Executive summary, 핵심 결론, 추천안 |
| 상세 근거 | 결론을 뒷받침하는 사실, 계산, 출처 | 근거 표, 출처 링크, 계산 근거 |
| 항목별 내역 | 큰 숫자나 결론을 구성하는 세부 항목 | 카테고리별 표, 항목별 상세표 |
| 가정 | 결론이 의존하는 전제 | assumption table, 가정 목록 |
| 불확실성 | 확인된 사실과 추정의 분리 | 확인됨, 추정, 확인 필요 |
| 대안/시나리오 | 주요 가정이 틀렸을 때의 선택지 | base/bull/bear, Plan A/B/C |
| 반대 관점 | 결론에 불리한 근거 | red-team, counterargument |
| 리스크/주의사항 | 실행 전 알아야 할 위험 | risk register, 주의사항 |
| 실행 체크리스트 | 사용자가 다음 행동으로 옮기는 목록 | 우선순위별 체크리스트 |
| 승인 지점 | AI가 자동 확정하지 않을 부분 | 사람 승인 필요, 최종 판단 보류 |

## 1.6 하네스 7요소 체크

| 요소 | 확인 질문 | 반영 위치 |
|---|---|---|
| 목표 | 무엇을 만들면 성공인가? | `harness/ORCHESTRATOR.md`, contracts |
| 컨텍스트 | AI가 먼저 읽어야 할 자료는 무엇인가? | contracts, artifacts README |
| 도구 | 조사, 파일 작성, 계산, 브라우저 등 어떤 도구가 필요한가? | platform adapter |
| 중간 산출물 | 다음 단계가 반드시 읽어야 할 파일은 무엇인가? | schemas, MANIFEST |
| 검증 | 품질을 어떻게 판단할 것인가? | rubrics, contracts |
| 권한과 승인 | 사람 확인 전 자동 처리하면 안 되는 것은 무엇인가? | ORCHESTRATOR, contracts |
| 기록과 개선 | 실행 후 무엇을 남길 것인가? | artifacts README, improvement-log |

## 1.7 단일 하네스와 복수 하네스 판단 기준

복잡한 업무를 무조건 하나의 하네스 안에 넣지 않는다.
전문 영역이 분리되고 각 영역이 독립적으로 재사용될 수 있으면 복수 하네스를 고려한다.

| 상황 | 권장 구조 |
|---|---|
| Phase가 7개 이하이고 문맥이 하나로 유지된다 | 단일 하네스 |
| Phase가 8개 이상이거나 전문 영역이 뚜렷하게 나뉜다 | 복수 하네스 검토 |
| 각 영역이 독립 산출물을 만들고 다른 업무에도 재사용된다 | 복수 전문 하네스 |
| 여러 전문 하네스의 결과를 묶어 최종 판단이 필요하다 | 상위 meta-orchestrator |
| 전문 하네스가 10개 이상이고 영역 그룹이 뚜렷하다 | 3단 구조도 고려 |

2단 구조:

```text
상위 meta-orchestrator
└── 개별 전문 하네스들
```

3단 구조:

```text
상위 meta-orchestrator
└── 중간 meta-orchestrator
    └── 개별 전문 하네스들
```

상위 meta-orchestrator는 각 하네스의 세부 작업을 대신하지 않는다.
각 하네스의 최종 산출물, 요약, 확인 필요, 사람 승인 지점을 읽어 전체 판단을 조율한다.

## 1.8 가치투자 복수 하네스 예시

가치투자 21단계는 하나의 거대한 하네스가 아니라 21개의 개별 전문 하네스로 설계할 수 있다.
각 하네스는 이 템플릿으로 독립 설계한다.

예시 그룹:

```text
[0. 투자 기준 설정]
        ↓
[1~2. 후보 발굴 / 빠른 선별]
        ↓
[3~7. 산업과 사업모델 이해]
        ↓
[8~11. 경쟁우위와 재무 품질 판단]
        ↓
[12~16. 미래 숫자와 가격 판단]
        ↓
[17~18. 최종 투자 결정과 비중 설정]
        ↓
[19~21. 사후 관리와 학습]
```

운영 원칙:

- 21개 하네스는 각자 독립적인 contract/procedure/schema/rubric/artifacts를 가진다.
- 상위 meta-orchestrator는 21개 하네스의 전체 순서와 의존 관계를 관리한다.
- 2단 구조와 3단 구조는 초기 운영 후 결정할 수 있다.
- 중간 meta-orchestrator를 둘 경우, 위 그룹처럼 영역별 묶음을 관리한다.
- 최종 투자 결정은 AI가 자동 확정하지 않고 사람 승인 지점으로 둔다.

## 1.9 Phase 설계 원칙

Phase는 많을수록 좋은 것이 아니다.
중간 판단이 독립적으로 검토되어야 하거나 다음 단계가 읽을 파일이 분명할 때 나눈다.

각 하네스의 Phase는 예시 흐름을 그대로 복사해서 만들지 않는다.
Phase는 해당 하네스의 목표, 입력 자료, 판단 단위, 중간 산출물, 검증 방식에 맞게 새로 설계한다.

Phase 설계 예시:

- 밸류에이션 하네스: 재무 정규화, 핵심 가정 설정, 시나리오 구성, DCF, 멀티플, 민감도, 검증, 최종 메모
- 밸류체인 하네스: 산업 구조, 공급자, 고객, 유통, 경쟁 구도, 병목, 협상력, 리스크
- Management 하네스: 경영진 이력, 자본배분, 주주친화성, 인센티브, 과거 발언 검증, 평판 리스크

각 Phase는 아래를 가져야 한다.

| 항목 | 의미 |
|---|---|
| 목적 | 이 Phase가 왜 필요한가 |
| 입력 | 이전 Phase 또는 사용자에게서 무엇을 읽는가 |
| 출력 | 어떤 파일을 어디에 저장하는가 |
| 최소 완료 기준 | 다음 Phase로 넘어가기 위한 조건 |
| 우수 산출물 기준 | 좋은 결과로 평가되기 위한 조건 |
| 금지사항 | 이 Phase가 하면 안 되는 일 |
| 실패 처리 | 정보 부족, 도구 실패, 충돌을 어떻게 남기는가 |

## 1.10 Phase 역할 후보 목록

아래 목록은 고정 순서가 아니다.
각 하네스의 목적에 맞게 선택, 병합, 삭제, 재배열한다.

| 역할 후보 | 의미 |
|---|---|
| 입력 정리 | 사용자 입력, 범위, 대상, 제약 조건을 확정한다 |
| 자료 수집 | 필요한 원자료, 출처, 데이터, 문서를 모은다 |
| 자료 품질 평가 | 출처 신뢰도, 최신성, 누락, 편향을 확인한다 |
| 사실 레이어 구성 | 확인된 사실과 해석을 분리한다 |
| 분석 | 해당 하네스의 핵심 계산, 비교, 판단을 수행한다 |
| 시나리오/대안 | 주요 가정이 달라질 때 결과가 어떻게 바뀌는지 본다 |
| 반대 관점 검토 | 결론에 불리한 근거와 실패 가능성을 검토한다 |
| 최종 산출물 작성 | 사용자가 판단하거나 실행할 수 있는 문서로 통합한다 |
| 검증 | 계산 오류, 논리 비약, 누락, 모순을 점검한다 |
| 개선 기록 | 다음 실행을 위해 문제와 개선점을 남긴다 |

## 1.11 최소 완료 기준과 우수 산출물 기준 분리

각 Phase의 contract에는 최소 완료 기준과 우수 산출물 기준을 분리한다.

```md
## 최소 완료 기준
- 필수 입력을 읽었다.
- 필수 출력 파일을 만들었다.
- 필수 섹션이 빠지지 않았다.

## 우수 산출물 기준
- 사용자가 실제 판단 또는 실행에 사용할 수 있을 만큼 상세하다.
- 결론, 근거, 가정, 불확실성, 대안이 분리되어 있다.
- 큰 숫자나 중요한 판단은 항목별 내역으로 풀려 있다.
- 다음 단계가 읽어야 할 핵심 정보가 누락되지 않았다.
- 사람 승인 또는 추가 확인이 필요한 지점이 명시되어 있다.
```

최소 완료 기준은 다음 Phase로 넘어갈 수 있는 기준이다.
우수 산출물 기준은 모델 간 비교와 품질 개선의 기준이다.

## 1.12 중간 산출물 보존 규칙

최종 산출물 단계는 이전 Phase의 중요한 정보를 버리면 안 된다.

최종 산출물을 저장하기 전에 이전 Phase 산출물을 다시 확인한다.

- 핵심 결론이 최종 산출물에 반영됐는가?
- 중요한 숫자와 계산 근거가 보존됐는가?
- 출처와 확인 필요 항목이 빠지지 않았는가?
- 주의사항과 리스크가 요약 과정에서 사라지지 않았는가?
- 대안과 실패 시나리오가 충분히 남아 있는가?
- 체크리스트가 사용자가 행동할 수 있는 형태인가?

요약은 허용된다.
하지만 핵심 근거, 위험, 확인 필요, 사람 승인 지점은 요약 과정에서 삭제하면 안 된다.

## 2.2 run-id 생성 규칙

run-id는 실행 결과물의 충돌을 막고, 반복 실행을 추적하기 위한 식별자다.

기본 형식:

```text
run-YYYYMMDD-{target}
```

예시:

```text
run-20260602-aapl
run-20260602-samsung
run-20260602-valuechain-aapl
run-20260602-valuation-aapl
```

충돌 처리:

```text
run-YYYYMMDD-{target}-v2
run-YYYYMMDD-{target}-v3
```

비교 모드:

```text
run-YYYYMMDD-{target}-claude
run-YYYYMMDD-{target}-codex
comparison-run-YYYYMMDD-{target}.md
```

복수 하네스 또는 가치투자 하네스 권장 형식:

```text
run-YYYYMMDD-{harness-name}-{ticker}
run-YYYYMMDD-{harness-name}-{ticker}-v2
```

규칙:

- 기존 폴더가 있으면 덮어쓰지 않는다.
- 같은 대상의 재실행은 `-v2`, `-v3`를 붙인다.
- 비교 모드는 Claude와 Codex 결과 폴더를 분리한다.
- 상위 meta-orchestrator 실행은 `run-YYYYMMDD-meta-{target}` 형식을 사용할 수 있다.

## 2.3 Contract 템플릿

```md
# {Phase Name} Contract

## 목적
이 Phase가 달성해야 하는 일을 한 문단으로 쓴다.

## 활성화 조건
- 언제 이 Phase를 실행하는가
- 어떤 이전 산출물이 있어야 하는가

## 입력
- `artifacts/{run-id}/...`
- 사용자 입력 또는 참고 자료

## 출력
- `artifacts/{run-id}/...`

## 산출물 깊이
- 기본값: {빠른 요약 / 표준 리포트 / 의사결정급 산출물}

## 최소 완료 기준
- 필수 입력을 읽었다.
- 필수 출력 파일을 저장했다.
- schema의 필수 섹션이 빠지지 않았다.

## 우수 산출물 기준
- 사용자가 실제 판단 또는 실행에 사용할 수 있을 만큼 상세하다.
- 결론, 근거, 가정, 불확실성, 대안이 분리되어 있다.
- 중요한 숫자와 판단은 항목별 내역으로 풀었다.
- 확인 필요와 사람 승인 지점을 명시했다.

## 금지사항
- 확인되지 않은 정보를 확정 사실처럼 쓰지 않는다.
- 중요한 가정이나 리스크를 숨기지 않는다.
- 다음 Phase가 필요한 핵심 정보를 생략하지 않는다.
- 플랫폼별 도구명이나 모델명을 업무 규칙으로 넣지 않는다.

## 실패 처리
- 자료가 부족하면 `[확인 필요: {이유}]`로 남긴다.
- 도구가 실패하면 실패 사실과 영향 범위를 기록한다.
- 결론을 낼 수 없으면 억지 결론 대신 판단 보류 조건을 쓴다.

## 사람 승인 필요
- AI가 자동 확정하면 안 되는 결정 또는 실행 지점을 쓴다.

## 수행 방법
`harness/procedures/{phase}.md`를 읽고 따른다.
```

## 2.4 Procedure 템플릿

```md
# {Phase Name} 수행 절차

1. 입력 파일이 존재하는지 확인한다.
2. contract, schema, 필요한 rubric을 읽는다.
3. 사용자의 목표와 이번 실행의 산출물 깊이를 확인한다.
4. 확인된 사실, 추정, 확인 필요를 분리한다.
5. 핵심 작업을 수행한다.
6. 중요한 계산, 판단, 출처, 가정을 표로 남긴다.
7. 산출물 깊이에 맞는 대안, 반대 관점, 실패 시나리오를 검토한다.
8. 이전 산출물의 핵심 정보가 누락되지 않았는지 확인한다.
9. 최소 완료 기준과 우수 산출물 기준을 자체 점검한다.
10. `harness/schemas/{phase}.schema.md` 형식에 따라 산출물을 저장한다.
11. 다음 Phase로 넘길 짧은 요약과 확인 필요 항목을 반환한다.

## 자체 점검 질문

- 결론만 있고 근거가 빈약하지 않은가?
- 중요한 숫자의 구성 항목이 보이는가?
- 출처 또는 입력 자료와 연결되는가?
- 불확실한 내용을 확정적으로 쓰지 않았는가?
- 반대 근거 또는 실패 가능성을 검토했는가?
- 사용자가 다음 행동을 알 수 있는가?
```

## 2.5 Schema 템플릿

Schema는 산출물 깊이에 따라 달라져야 한다.
아래 세 단계 중 하나를 선택한다.

### 빠른 요약 schema

```md

## 필수 섹션

1. 핵심 요약
   - 현재 결론
   - 중요한 근거 3개 이하

2. 확인된 정보
   - 사용자가 준 입력
   - 확인된 사실

3. 확인 필요
   - `[확인 필요: {이유}]`

4. 다음 행동
   - 다음 Phase 또는 사용자 확인 사항
```

```md

`artifacts/{run-id}/{file-name}`가 따라야 할 형식.

## 산출물 깊이
- 표준 리포트

## 필수 섹션

1. 핵심 요약
   - 최종 결론 또는 현재 판단
   - 가장 중요한 근거 3-5개

2. 입력과 범위
   - 사용자가 준 입력
   - 포함한 범위
   - 제외한 범위

3. 상세 근거
   - 항목
   - 확인된 사실
   - 출처 또는 입력 파일
   - 확인 필요

4. 분석 또는 산출물 본문
   - 업무별 핵심 결과
   - 항목별 상세 내역

5. 불확실성 및 리스크
   - 확인된 사실
   - 추정
   - 확인 필요
   - 주요 리스크

6. 대안 또는 시나리오
   - 기본안
   - 대안
   - 실패 시 대응

7. 실행 체크리스트
   - 최우선
   - 추가 확인
   - 후속 실행
```

### 의사결정급 산출물 schema

```md
# {Phase Name} Output Schema

2. 입력과 범위
   - 사용자가 준 입력
   - 포함한 범위
   - 제외한 범위
   - 사용한 원자료

3. 사실 레이어
   - 확인된 사실
   - 출처
   - 신뢰도
   - 최신성

4. 가정과 계산
   - 핵심 가정
   - 계산 방식
   - 항목별 내역
   - 민감도 또는 변경 조건

5. 분석
   - 긍정 근거
   - 부정 근거
   - 핵심 쟁점
   - 해석

   - base
   - bull
   - bear
   - 각 시나리오에서 달라지는 판단

9. 실행 체크리스트
   - 최우선
   - 추가 확인
   - 후속 실행
   - `▶ 사람 승인 필요: {내용}`

10. 다음 Phase 전달 요약
   - 다음 Phase가 반드시 읽어야 할 핵심 정보
```

## 2.6 Rubric 템플릿

```md
# {Harness Name} Judge Rubric

모든 항목은 1-5점 척도이며, 가중치를 적용해 100점 만점으로 환산한다.
도메인별로 항목과 가중치는 조정할 수 있다.

## 평가 항목

| 항목 | 가중치 | 평가 질문 |
|---|---:|---|
| 업무 완결성 | 20% | 요청한 범위와 필수 산출물이 모두 충족됐는가? |
| 근거 추적성 | 15% | 결론이 입력 자료, 출처, 계산과 연결되는가? |
| 분석 깊이 | 15% | 표면적 요약이 아니라 원인, 구조, 숫자, 의미를 분석했는가? |
| 불확실성 분리 | 10% | 확인된 사실, 추정, 확인 필요가 구분됐는가? |
| 대안/반대 관점 | 10% | 대안, 실패 시나리오, 반대 근거를 검토했는가? |
| 실행 가능성 | 10% | 사용자가 다음 행동을 알 수 있는가? |
| 최종 산출물 사용성 | 10% | 최종 파일이 실제 검토, 실행, 승인에 쓰기 좋은가? |
| 체크리스트 품질 | 5% | 체크리스트가 우선순위별, 상황별로 정리됐는가? |
| 사람 승인 안전성 | 5% | AI가 자동 확정하면 안 되는 지점을 남겼는가? |

## 점수 기준

5점: 사용자가 바로 의사결정 또는 실행에 활용할 수 있다.
4점: 대부분 충분하나 일부 상세 또는 검증이 부족하다.
3점: 기본 구조는 있으나 중요한 근거, 대안, 확인 필요가 부족하다.
2점: 형식은 있지만 실제 사용하기 어렵다.
1점: 필수 정보가 빠졌거나 판단을 왜곡할 수 있다.
```

가치투자 하네스는 `재무 계산 정확성`, `밸류에이션 민감도`, `리스크 식별`, `원자료 품질`, `반대 thesis 검토`의 가중치를 높일 수 있다.

5. 각 Phase 완료 후 출력 파일이 존재하는지 확인한다.
6. 최종 산출물 작성 시 이전 산출물 보존 점검을 수행한다.
7. 비교 모드라면 Judge rubric에 따라 비교 리포트를 생성한다.
8. 비교 리포트에 비교 방식, 공유 입력 파일, 실행 폴더, 비교 범위를 기록한다.
9. `artifacts/improvement-log.md`에 개선 기록을 남긴다.

## 중단 조건

- 필수 입력이 없고 합리적 가정도 불가능한 경우
- 도구 실패로 핵심 자료를 확인할 수 없는 경우
- 사람 승인 없이 진행하면 위험한 경우

- meta-orchestrator와 하위 하네스 사이의 입력/출력 연결 문제

## 4.3 최종 체크리스트

새 하네스 청사진 또는 파일 구성을 마치기 전에 확인한다.

- [ ] 최종 산출물이 무엇인지 분명하다.
- [ ] 산출물 깊이가 정해져 있다.
- [ ] 단일 하네스와 복수 하네스 판단이 끝났다.
- [ ] meta-orchestrator 필요 여부가 검토됐다.
- [ ] run-id 규칙과 충돌 처리 규칙이 있다.
- [ ] 최소 완료 기준과 우수 산출물 기준이 분리되어 있다.
- [ ] schema가 산출물 깊이에 맞게 선택됐다.
- [ ] schema가 단순 목차가 아니라 정보 밀도까지 지정한다.
- [ ] procedure가 이전 산출물 보존 점검을 포함한다.
- [ ] rubric이 실제 사용자 체감 품질을 평가한다.
- [ ] 확인 필요, 추정, 사람 승인 표기 규칙이 통일됐다.
- [ ] 비교 모드에서 입력 공유 / 각자 생성 방식이 명시됐다.
- [ ] 불확실성, 대안, 반대 관점, 사람 승인 지점이 빠지지 않았다.
- [ ] Claude/Codex adapter가 공통 원장을 참조하는 얇은 구조다.
- [ ] Codex orchestrator Skill이 전체 진입점으로 추가됐다.
- [ ] `MANIFEST.md`, `AGENTS.md`, `CLAUDE.md`, `artifacts/README.md` 템플릿이 반영됐다.
- [ ] 실행 결과와 개선 기록이 `artifacts/`에 남는다.
- [ ] 다음 하네스 생성자가 이 문서만 읽고도 같은 구조를 재현할 수 있다.

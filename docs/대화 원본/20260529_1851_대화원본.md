**Assistant**: ## CRUD 기초

**CRUD**는 데이터를 다루는 4가지 기본 작업입니다.

| 작업 | 의미 | HTTP | SQL |
|------|------|------|-----|
| **C**reate | 생성 | POST | INSERT |
| **R**ead | 조회 | GET | SELECT |
| **U**pdate | 수정 | PUT/PATCH | UPDATE |
| **D**elete | 삭제 | DELETE | DELETE |

간단한 예: 블로그 게시글 API

```
POST   /posts        → 글 작성
GET    /posts/123    → 글 조회
PATCH  /posts/123    → 글 수정
DELETE /posts/123    → 글 삭제
```

## 대기업 비즈니스로의 확장

**1. 성능 문제 → 캐싱 & 읽기 분리**
- Read가 압도적으로 많음 → Redis 캐시, DB 읽기 전용 복제본(Read Replica) 분리

**2. 단일 DB 한계 → 샤딩 & 마이크로서비스**
- 주문/유저/상품을 각각 독립 서비스로 분리
- 각 서비스가 자신의 DB를 소유 (서비스당 CRUD)

**3. 데이터 일관성 문제 → 이벤트 기반 아키텍처**
- 주문 생성(Create) → Kafka 이벤트 발행 → 재고 차감, 결제 처리 비동기 진행
- 단순 DB 트랜잭션 대신 **Saga 패턴** 등으로 분산 트랜잭션 처리

**4. 감사·규정 요구 → Soft Delete & 이력 관리**
- `DELETE` 대신 `is_deleted = true` (Soft Delete)
- 모든 변경 이력을 별도 테이블에 기록 (금융, 의료 등 법적 요구)

**5. 대규모 Read → CQRS 패턴**
- 쓰기(Command)와 읽기(Query) 모델을 완전히 분리
- 읽기용 데이터는 ElasticSearch, DynamoDB 등 목적에 맞는 DB에 따로 저장

**한 줄 요약:** CRUD는 변하지 않지만, 대기업에서는 그 CRUD를 *어디서, 어떻게, 어떤 순서로* 실행하느냐가 아키텍처의 핵심이 됩니다.
